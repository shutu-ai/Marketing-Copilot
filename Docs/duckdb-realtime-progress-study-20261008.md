# DuckDB 实时入库进度写入与恢复方案研究

日期：2026-10-08。状态：设计研究，尚未修改业务代码或部署。本次以当前工作区代码、前一轮远端采样及本地 DuckDB 1.2.0 实验为依据。

## 结论与实施顺序

推荐先实施“短显式事务 + 合并进度 + 有界节流 + 租约校验 + 可靠重试恢复”，再单独实施批量去重。第一批变化优先解决写冲突引起的额外等待、状态不一致和文件滞留；第二批变化针对约 2,000–2,600 行文件仍耗时数十秒的问题。

采用渐进式优化，保持短信与文件任务的业务提交点清晰，避免一次性将所有数据库调用改成自动长事务。TPS 是否提高、提高多少，必须通过相同负载和独立发送指标验证。

| 证据 | 已确认事实 | 解释范围 |

| 当前代码 | progress 分别调用两张表的更新，各自建立连接并 commit | 两个数据库往返和两个独立写入边界；存在部分成功 |

| 当前代码 | update_progress、schedule_retry、完成更新未按领取 token 限定；recover_expired_files 只在 start_worker 调用 | 存在旧 worker 覆盖状态、失败处理后的文件等待重启才恢复的风险 |

仍缺少扫描、读取、匹配、去重、任务入库、归档的独立耗时分布。当前 phase 日志之间的时间也包含进度更新本身的等待，不能直接当作对应计算阶段耗时。

官方依据：[事务管理](https://duckdb.org/docs/current/sql/statements/transactions)、[并发与事务冲突](https://duckdb.org/docs/current/connect/concurrency)。这些页面是当前版本文档；版本敏感的事务行为另用本地 1.2.0 验证。Context7 查询失败，未用其返回内容作为依据。

## 1. 进度更新：一个短显式事务

新增统一进度写入入口，接收 ingestion_file_id、processed_file_id、lease_token、worker_id、当前 phase、行数、chunk 信息和白名单版本。

```text
准备好不可变进度快照
→ 获取现有应用写锁
→ BEGIN TRANSACTION
→ 校验 ingestion_files 仍为 processing 且 token 为当前领取者
→ 更新 ingestion_files，RETURNING 校验实际更新成功
→ 更新 processed_files
→ COMMIT
→ 释放写锁
```

任意更新或提交失败均整体回滚并释放锁。无匹配 token 表示已失去处理权，不能更新第二张表，也不能再完成或重试该文件。用 RETURNING 验证，避免依赖不可靠的 rowcount。

两条 UPDATE 仍然存在，但数据库连接、锁获取与事务提交合并。预期减少每次进度报告的事务开销；不会仅因为 SQL 条数不变就声称数据库工作减半。

该事务只包含数据库状态写入。CSV 读取、白名单查找、Python 模板处理、文件移动、等待和退避都放在事务外。不得用一个事务包住完整文件处理过程。

可为原 update_progress/update_file_progress 增加“使用调用者连接”的内部函数，再由统一入口管理事务。保持旧入口兼容其他调用者，避免全局改变所有连接的隐式行为。

## 2. 节流：按整个文件合并，而非每个阶段单独计时

建议初始进度最小持久化间隔为 2 秒。这是拟新增配置，当前部署尚未支持。

| 事件 | 策略 |
|---|---|
| 领取与开始处理 | 同步持久化领取状态 |
| reading_input、loading_index、matching、enqueueing_tasks 等展示进度 | 内存保存最新快照；全文件统一计时，至多每 2 秒写一次 |
| 需要持久化的 chunk 检查点 | 按原业务边界立即提交，不被展示节流跳过 |
| completed、failed、retrying、expired、quarantined | 立即持久化最终/控制状态，取消旧进度快照 |
| 租约心跳 | 独立于展示更新，必须在租约到期前续租 |

matching 与 enqueueing_tasks 在多 chunk 文件中交替出现，因此“阶段改变就立即提交”会绕过节流。短暂展示阶段可以被后一阶段合并，页面展示当前阶段即可；精确阶段耗时通过内存计时指标记录。

第一版可采用 worker 内的文件级进度报告器：到达间隔才同步提交；普通进度写失败保留最新快照，下一次机会重新提交，不立即重跑整个文件。函数内持续运行的长 chunk 应在安全批次边界检查心跳；只有 progress 回调处检查间隔并不能保证长时间计算的心跳。

若性能测量证实同步等待仍占明显比例，再增加独立进度线程：每个活动文件仅保留一个最新快照，使用线程自有连接，周期刷新；合并容器有界，且必须处理 token、版本序号及终态取消。第一版不必引入全局异步写入队列。

## 3. 错误分类与整笔事务重试

将 progress("loading_index") 移出打开白名单索引的异常捕获范围。只有 duckdb.connect(index_path) 或索引表验证的失败才按索引依赖处理。主库进度写冲突归类为 TRANSIENT_DB，不设置白名单 building，也不触发重建。

对新增的短事务增加有限重试，例如最多 3 次，带短退避与随机抖动。每次尝试必须回滚、关闭连接、释放锁，然后以新连接重新开始整个事务。不能在失败的事务内重复执行最后一条 SQL，也不能在持锁时 sleep。

普通展示进度在重试预算用尽后继续保留快照并记录计数，允许业务计算推进。领取、任务创建、chunk 完成、重试计划及文件终态属于业务状态，不能默默跳过。其失败应进入受控恢复路径。

重试总耗时包含锁等待和 SQL 执行。默认 5 秒锁等待乘以多次重试会导致数十秒停顿；需要为普通进度设计可选的较短获取锁预算，而非盲目提高全局锁超时。SQL 执行是否需要超时/中断必须单独研究，不能把锁获取超时当作 SQL 执行上限。

## 4. 文件租约与恢复必须随同修复

当前 schedule_retry 会增加 retry_count，直接重试整函数可能重复增加。应采用 token 条件更新：只允许 processing 且 token 匹配的记录转为 retrying，RETURNING 确认更新；重放时先读取状态，识别已经成功的转换，确保 retry_count 只增加一次。

完成与失败操作同样校验 token。完成先取消该文件待写展示进度，阻止旧快照将 completed 覆盖为 matching。后台报告器如被引入，必须用 token 和单调序号防止过期快照覆盖。

将 recover_expired_files 加入已有互斥维护流程，建议初始每 30 秒检查一次。回收前先验证租约确实到期，不能仅以 last_progress_at 不更新就认为 worker 死亡。持续工作的 worker 需要定期续租，间隔不超过当前租约的三分之一。

若失败状态也无法持久化：保留文件、输出限频错误、停止该 worker 继续使用旧 token；租约自然到期后由恢复流程重新领取。实际发生中途重试时，已有稳定任务 dedupe_key 和 chunk 记录应阻止重复建任务，但须用测试验证，不能据此承诺短信 exactly-once。

文件移动与数据库事务不能共同原子提交。完成流程还需处理“文件已移动到 received、数据库完成失败”的重试：先核对两个位置及已完成 chunk，再补齐元数据，不重新发送。此项应与终态恢复测试一起设计。

## 5. 文件处理吞吐：后续改为批量去重

当前 CSV 路径为每个有效号码调用临时 DuckDB 的 INSERT ... ON CONFLICT ... RETURNING，即使该文件完全不命中白名单也如此。2,500 个号码约产生 2,500 次 Python/SQL 调用。该库独立于主库，不应把它的全部耗时归为主数据库写锁。

下一步采用有界 chunk 批量去重：

1. 保留输入行号，对 chunk 内号码按首次出现去重。
2. 用批量输入关系与 seen_msisdns 做 anti-join，识别跨 chunk 首次出现号码。
3. 将首次出现号码及 matched 标记一次性写入临时去重库。
4. 只把首次出现且命中白名单的输入行用于创建任务。

必须保持首次行取值、号码规范化、无效行统计、跨 chunk 去重、匹配行数和唯一匹配用户数等现有语义。大文件仍分块、临时去重仍可落盘，不以全文件 Python set 代替。

campaign 8 的零匹配文件也要完成正确匹配，不能依据此前全为 0 就跳过后续文件。需另行核对其号码格式和白名单配置是否导致持续零匹配；这是待验证事项，尚非已确认缺陷。

## 6. 扫描优化的实际边界

最新本地 watcher 已进行文件名权威时间过滤与目录变化检查。不过目录 mtime 变化或每分钟桶变化仍会触发完整扫描，30 秒不是强制最小扫描间隔；连续落新文件时仍可能频繁 enumerate 和 sort。

先记录扫描耗时、枚举数、有效候选数、跳过原因与复制数。若扫描仍占明显 CPU，再考虑按日目录或“目录事件提示 + 周期对账”，并给重复候选加有界缓存。文件可能迟到，不能以最大的已处理文件名作为唯一水位直接跳过所有较小文件名。

历史日期文件按已有策略忽略；当天积压的旧小时文件是否过期，需要业务时效规则，不能自动把“历史日期”扩大为“不是当前分钟”。

## 7. 改动范围与验证标准

| 模块 | 拟改动 |
|---|---|
| database.py | 提供显式短事务/可选锁预算入口，完整释放锁；不全局自动 BEGIN |
| operations_service.py、ingestion_job_service.py | 支持统一连接更新；领取 token 校验；幂等重试和终态处理 |
| realtime_campaign_service.py | 统一报告器、节流、错误分类分离；下一批替换逐行去重 |
| realtime_ingestion_worker.py | token 传递、续租、周期恢复、失败写入再失败的兜底 |
| metrics_service.py | 输出阶段计时、实际进行中的 phase 和进度失败计数 |

当前 phase gauge 汇总全部记录，部分标签可能残留，并不等于当前活跃 worker 数。新增活跃阶段指标应仅统计 status=processing，消失标签要清零，展示历史状态和活跃状态需分开。

验证包括：

- 第二张表失败时第一张表回滚，成功时两表一致；锁在各种异常后均释放。
- 高频、交替阶段回调受文件级间隔限制，最后状态立即提交；重试时不回退行数。
- 进度冲突不转成白名单错误、不重建索引、不重跑已经完成的 chunk。
- retry_count 在同一控制转换重放后只增加一次。
- 旧 token 无法更新新领取者记录；普通进度无法覆盖终态。
- 租约到期且 worker 已失效的文件在运行时恢复；健康长任务不被误回收。
- CSV 不同 chunk、重复号码、零匹配、语言字段、输入首行选择等结果与旧版本一致。
- 文件已归档但终态落库失败、服务重启等场景不会丢文件或重复创建任务。

线上 A/B 保持 worker、claim batch、窗口、连接数和活动文件范围一致。先 15–30 分钟，再跨较长业务窗口观察，采集每个 campaign 文件数/分钟、文件处理 p50/p95、各阶段耗时、进度提交数/秒、锁等待与超时增量、最老 processing 租约年龄、队列和 Web 延迟。

发送指标使用 send_message、submit_sm_resp 与任务数三个独立计数器在同一采样区间的增量，分别衡量分片发送、分片响应、完整任务完成。滚动一分钟快照可用于趋势，但不能把不同时间口径的数值直接相减当作丢消息。

验收要求是：业务结果不变、无孤立 processing/旧 token 覆盖、进度提交数量下降、锁超时与文件 p95 不劣化；发送供给充足时独立发送速率改善。由于目前缺少各阶段精确基线，不提前承诺提高到 300/400 TPS。

## 方案自查

本方案修正了三个容易误导的说法：同连接 commit 不自动产生多语句事务；阶段变化立即写入可能使节流失效；零匹配和 finalizing 日志不能单独证明白名单或归档环节的真实计算耗时。

仍需实测主库冲突的全部触发源。当前锁是应用进程内的门禁，不能承诺所有 DuckDB 写冲突都由进度更新引起。批量去重、显式事务和恢复机制应分批验证，以便定位收益或回归。
