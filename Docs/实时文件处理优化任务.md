## 2. 当前问题与证据

2026-09-09 线上升级及排查日志显示：

手工重启后的进程检查显示：

- 主进程 CPU 约 `177%`，不是空闲状态；
- 当前打开的输入文件为：`Exhibition_Center_20260909143828_526_232.csv`；
- 同时打开约 78 MB 的 `whitelist.csv`；
- 同时创建并写入临时 `whitelist.duckdb` 和 WAL 文件；
- 白名单约 `4,123,012` 行。

### 2.2 当前实现行为

当前调度器先同步监听目录，再同步处理 inbox：

```text
sync_watch_dirs_to_inboxes()
process_realtime_inboxes()
等待下一轮
```

相关代码：

- 调度顺序：[backend/services/activity_scheduler.py](../backend/services/activity_scheduler.py:97)
- 监听目录复制：[backend/services/realtime_campaign_service.py](../backend/services/realtime_campaign_service.py:893)
- inbox 处理：[backend/services/realtime_campaign_service.py](../backend/services/realtime_campaign_service.py:973)
- 每个文件加载白名单：[backend/services/realtime_campaign_service.py](../backend/services/realtime_campaign_service.py:442)
- 成功完成后才写入实时文件记录：[backend/services/realtime_campaign_service.py](../backend/services/realtime_campaign_service.py:672)

### 2.3 根因判断

当前问题不是升级删除或丢失监听文件，而是以下组合导致的处理阻塞：

1. 每个输入文件都重复导入整份白名单；
2. 白名单导入在单个文件处理流程内同步执行；
3. 监听目录同步和 inbox 摄取共用一个调度线程；
4. 单个文件处理期间没有阶段性进度日志；
5. 文件失败后缺少明确的重试退避和错误分类。

当前复杂度近似为：

```text
白名单总成本 × 文件数量 + 文件处理成本
```

目标复杂度应为：

```text
白名单索引构建一次 + 各文件处理成本
```

## 3. 目标与非目标

### 3.1 目标

- 白名单上传后只构建一次可复用索引；
- 监听目录扫描不再被单个大文件处理阻塞；
- 文件处理可按 chunk 恢复，服务重启不丢失进度；
- 页面和日志可明确显示当前文件、阶段、进度和错误；
- 失败文件按错误类型重试，避免每 3 秒无限重复；
- 白名单更新过程中不影响正在处理的文件；
- 支持 400 万级白名单和持续输入文件场景；
- 不改变短信业务规则、号码匹配规则和已完成文件去重规则。

### 3.2 非目标

- 本任务不改变短信发送状态定义；
- 本任务不改变 accepted/delivered 统计规则；
- 本任务不引入多进程 DuckDB 写入；
- 第一阶段不盲目增加实时文件并行度；
- 不通过删除 `processed_files`、`inbox` 或数据库记录来“清空卡住状态”。

## 4. 总体目标架构

```text
监听目录
   │
   │ 轻量同步，持续运行
   ▼
campaign inbox
   │
   │ 只登记待处理任务，不在调度器中执行重处理
   ▼
实时摄取队列 / ingestion_jobs
   │
   │ 独立 worker，初始并发度=1
   ▼
文件处理器
   ├── 读取持久化白名单索引
   ├── 分 chunk 匹配号码
   ├── 生成短信任务
   ├── 保存 chunk 进度
   └── 完成后移动到 received
   │
   ▼
processed_files + ingestion_chunks + realtime_campaign_files
```

白名单更新采用版本化：

```text
上传临时文件
   ▼
构建 whitelist index vN
   ▼
校验行数、索引、文件 hash
   ▼
原子切换 active_whitelist_version
   ▼
后续文件使用新版本；已开始文件继续使用其绑定版本
```

## 5. 优先级 P1：持久化白名单索引

### 5.1 目标

将白名单从“每个文件重复加载”改为“上传或更新时构建一次，文件处理时只查询”。

### 5.2 实施任务

#### P1.1 增加白名单索引实体

建议增加独立的白名单索引元数据，避免与实时活动主表字段混杂：

```text
realtime_whitelist_versions
├── id
├── campaign_id
├── version_no
├── source_filename
├── source_path
├── source_hash
├── row_count
├── normalized_count
├── index_path
├── status              # building / ready / failed / retired
├── error_detail
├── created_at
├── ready_at
└── retired_at
```

在 `realtime_campaigns` 或单独关联表中记录：

```text
active_whitelist_version_id
```

在 `processed_files` 或 `ingestion_files` 中记录：

```text
whitelist_version_id
```

#### P1.2 构建持久化 DuckDB 索引

每个白名单版本生成独立文件，例如：

```text
<campaign_dir>/whitelist/index/whitelist-v000003.duckdb
```

索引表最少包含：

```sql
CREATE TABLE whitelist_msisdns (
    msisdn TEXT PRIMARY KEY,
    language TEXT NOT NULL DEFAULT ''
);
```

必须满足：

- `msisdn` 使用与现有发送流程相同的标准化规则；
- 重复号码只保留一条；
- 语言字段保持现有优先级和空值语义；
- 索引文件构建完成前不能成为 active 版本；
- 构建失败必须留下 `error_detail`，不能静默切换。

#### P1.3 改造上传流程

上传流程改为：

1. 保存上传源文件到临时版本目录；
2. 计算文件 hash；
3. 创建 `building` 版本；
4. 后台构建索引；
5. 校验行数和索引可查询性；
6. 将版本置为 `ready`；
7. 原子更新活动的 active 版本；
8. 旧版本延迟清理。

上传接口不能等待整个白名单导入完成后长期占用 HTTP 请求。接口应返回：

```json
{
  "version_id": 3,
  "status": "building",
  "row_count": 4123012
}
```

#### P1.4 改造文件处理流程

`receive_file()` 不再创建临时 `mc-whitelist-*` 数据库，不再逐文件导入 `whitelist.csv`。

处理流程改为：

1. 获取活动当前 active 白名单版本；
2. 将版本绑定到当前文件；
3. 以只读方式打开该版本索引；
4. 按输入文件 chunk 查询匹配号码；
5. 文件完成后保留版本绑定信息。

如果没有 `ready` 版本，文件进入 `waiting_for_whitelist`，不得标记为普通失败并每 3 秒重试。

#### P1.5 白名单更新并发规则

白名单更新时必须满足：

- 已经开始处理的文件继续使用它绑定的旧版本；
- 新文件使用新 active 版本；
- 不直接覆盖正在读取的 `whitelist.csv`；
- 新索引构建失败时继续保留旧的 ready 版本；
- 旧版本至少保留到所有绑定文件结束或进入终态。

### 5.3 P1 验收标准

- 412 万行白名单只被导入一次；
- 第二个及后续文件不再产生新的 `mc-whitelist-*` 临时库；
- 白名单更新期间正在处理的文件不报文件不存在或读取失败；
- 新白名单构建失败不会破坏旧版本；
- 服务重启后可以继续使用 ready 版本；
- 旧文件和新文件可以通过 `whitelist_version_id` 追溯匹配依据；
- 4,123,012 行白名单索引可在目标 SLES12SP5 环境完成构建和查询。

### 5.4 P1 测试任务

- `TST-P1-001`：10 万行白名单构建并查询；
- `TST-P1-002`：412 万行白名单构建并查询；
- `TST-P1-003`：同一白名单处理 100 个输入文件，确认只构建一次；
- `TST-P1-004`：构建中重启服务，确认版本最终为 ready 或 failed；
- `TST-P1-005`：处理文件过程中上传新白名单，确认旧文件和新文件使用正确版本；
- `TST-P1-006`：索引文件损坏，确认标记损坏版本并回退到最近可用 ready 版本，给出可诊断事件和错误。

## 6. 优先级 P2：监听与文件处理解耦

### 6.1 目标

将目录监听从重型文件处理流程中解耦，保证单个文件处理很慢时，监听仍然可以继续发现和登记新文件。

### 6.2 实施任务

#### P2.1 调整调度器职责

调度器只负责：

- 扫描活动监听目录；
- 将文件复制到 inbox；
- 登记或刷新 `ingestion_files`；
- 投递待处理文件；
- 执行轻量级状态维护。

调度器不能直接同步执行完整 `receive_file()`。

#### P2.2 增加实时摄取 worker

新增独立的 realtime ingestion worker：

- 初始并发度固定为 1；
- 从 `ingestion_files` 或队列中领取 pending 文件；
- 使用现有 chunk lease 机制；
- 完成、失败或中断后更新数据库；
- 不影响调度器继续扫描监听目录。

第一阶段不增加多个实时写入 worker，避免 DuckDB 主数据库并发写入复杂度；先实现“监听不被阻塞”。

#### P2.3 文件领取规则

领取文件时必须使用原子状态变更：

```text
pending → processing
```

只有成功领取 lease 的 worker 才能处理文件。服务重启后：

```text
processing + lease expired → pending
```

#### P2.4 队列容量和背压

增加以下限制：

- 每个活动最多同时存在的 pending 文件数；
- 全局 inbox 最大积压数；
- 单文件大小限制；
- 白名单索引未 ready 时的等待状态；
- 处理速度低于输入速度时的告警。

监听目录同步不能无限复制文件导致磁盘耗尽。达到阈值后应：

- 停止继续复制新文件；
- 保留源文件；
- 记录 backpressure 日志和指标；
- 处理完成后自动恢复。

### 6.3 P2 验收标准

- 单个文件处理 30 分钟时，监听器仍能每个扫描周期发现新文件；
- 调度器日志不会因为一个文件长时间处理而停止；
- 同一个文件不会被两个 worker 同时处理；
- 服务重启后 processing 文件可恢复；
- inbox 达到上限时不会无限复制文件；
- 现有短信任务生成和重复文件规则不改变。

### 6.4 P2 测试任务

- `TST-P2-001`：人为延迟一个文件处理 30 分钟，确认监听仍工作；
- `TST-P2-002`：处理期间持续产生新文件，确认新文件进入 pending；
- `TST-P2-003`：处理文件中重启服务，确认 lease 过期后恢复；
- `TST-P2-004`：启动两个处理 worker，确认同一文件不会重复生成任务；
- `TST-P2-005`：inbox 达到上限，确认背压和恢复行为。

## 8. 优先级 P4：失败重试退避与错误分类

### 8.1 目标

避免失败文件每 3 秒无限重试，同时保留自动恢复能力。

### 8.2 实施任务

#### P4.1 错误分类

建议分类：

| 类型 | 示例 | 是否自动重试 |
|---|---|---:|
| `TRANSIENT_IO` | 临时文件不可读、短暂磁盘异常 | 是 |
| `TRANSIENT_DB` | 数据库锁、临时 DuckDB 锁 | 是 |
| `WAITING_DEPENDENCY` | 白名单索引尚未 ready | 是，长退避 |
| `INVALID_INPUT` | CSV 格式错误、列缺失 | 否，进入 quarantine |
| `INVALID_CAMPAIGN` | 活动配置无效、模板缺失 | 否，等待人工修复 |
| `RESOURCE_LIMIT` | 磁盘、内存、队列达到上限 | 是，指数退避 |
| `PERMANENT_DUPLICATE` | 文件已完成处理 | 否，归档 duplicate |
| `UNKNOWN` | 未分类异常 | 有限次数重试后告警 |

#### P4.2 增加重试字段

建议增加：

```text
retry_count
last_error_class
last_error_at
next_retry_at
max_retry_count
```

#### P4.3 退避策略

默认策略：

```text
第 1 次：30 秒
第 2 次：2 分钟
第 3 次：10 分钟
第 4 次：30 分钟
超过上限：failed，需要人工处理
```

具体时长应配置化，不能写死在业务分支中。

#### P4.4 人工恢复

页面需要支持：

- 查看失败原因和最后处理阶段；
- 重试单个文件；
- 批量重试可重试失败；
- 将永久失败文件归档；
- 查看重试次数和最后一次错误。

人工重试不能通过删除数据库记录实现，应使用显式状态迁移：

```text
failed → queued
```

### 8.3 P4 验收标准

- 失败文件不会每 3 秒重复消耗 CPU；
- 临时错误可自动恢复；
- 永久错误不会无限重试；
- 每次重试原因和次数可追溯；
- 人工重试不会重复生成已完成的短信任务。

### 8.4 P4 测试任务

- `TST-P4-001`：模拟白名单暂不可用，确认进入等待并退避；
- `TST-P4-002`：模拟 CSV 格式错误，确认进入 quarantine；
- `TST-P4-003`：模拟数据库锁，确认指数退避；
- `TST-P4-004`：超过最大重试次数，确认停止自动重试并告警；
- `TST-P4-005`：人工重试成功后不生成重复任务。

## 9. 优先级 P5：白名单批量导入和查询优化

### 9.1 目标

在 P1 持久化索引的基础上，缩短索引构建时间和查询时间，降低 Python 循环和重复转换开销。

### 9.2 实施任务

#### P5.1 批量导入

优先使用 DuckDB 批量导入或 `COPY`，减少逐行或逐块 `executemany()` 调用。

导入流程建议：

```text
CSV 原始文件
  ↓
批量导入 raw 表
  ↓
SQL 标准化号码
  ↓
去重并写入 whitelist_msisdns
  ↓
建立唯一约束/索引
```

必须通过测试确认 SQL 标准化结果与现有 `normalize_msisdn()` 完全一致；如果不能证明一致，则保留 Python 标准化作为兼容路径。

#### P5.2 分批查询

文件处理时继续按输入文件 chunk 查询，不把整个输入文件或整个白名单加载到 Python 内存。

要求：

- 查询参数数量有上限；
- chunk 大小可配置；
- 单个查询耗时可记录；
- 失败时能定位到 chunk；
- 查询结果不泄露到普通日志。

#### P5.3 资源控制

增加配置项：

```text
MC_REALTIME_WHITELIST_BUILD_MEMORY_LIMIT
MC_REALTIME_WHITELIST_BUILD_THREADS
MC_REALTIME_MATCH_CHUNK_SIZE
MC_REALTIME_INDEX_BUILD_TIMEOUT
```

默认值必须适配 SLES12SP5 目标机，不能只按开发机资源设置。

#### P5.4 索引维护

- 使用文件 hash 避免相同白名单重复构建；
- 旧索引按引用计数或保留窗口清理；
- 构建中产生的临时目录需要可恢复清理；
- 索引文件损坏时保留源文件并生成明确告警；
- 不在服务升级的 backend/frontend 目录替换过程中删除索引文件。

### 9.3 P5 验收标准

- 批量导入结果与现有号码标准化逻辑一致；
- 4,123,012 行白名单构建耗时可测量且不会无限等待；
- 同一 hash 的白名单不会重复构建；
- 查询内存不会随白名单总量线性增长到不可控；
- 目标机资源达到限制时有明确错误和恢复方式。

### 9.4 P5 测试任务

- `TST-P5-001`：小、中、大三档白名单性能基准；
- `TST-P5-002`：Python 标准化和 SQL 标准化结果对比；
- `TST-P5-003`：重复 hash 不重复构建；
- `TST-P5-004`：内存上限和线程上限测试；
- `TST-P5-005`：构建过程中磁盘空间不足；
- `TST-P5-006`：索引损坏后的恢复和回滚。

## 10. 实施顺序与门禁

  ↓
P4 失败重试退避

### 10.1 阶段门禁

## 12. 风险与控制措施

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 新旧号码标准化逻辑不一致 | 匹配数量变化 | 建立逐号码对比测试，未通过前保留兼容实现 |
| 白名单更新覆盖正在读取的文件 | 当前文件读取失败 | 版本化文件和原子切换 |
| 新 worker 与现有任务 worker 竞争数据库 | DuckDB 锁冲突 | 实时摄取并发度先固定为 1 |
| 处理进程重启造成重复任务 | 重复短信 | 复用文件 hash、chunk lease 和任务去重 |
| 索引文件占满磁盘 | 服务异常 | 版本保留策略、磁盘阈值和构建前空间检查 |
| 失败文件无限重试 | CPU 和日志耗尽 | 错误分类、指数退避和最大重试次数 |
| 监控增加敏感数据泄露 | 合规风险 | 日志脱敏，不输出手机号和正文 |
| 在线升级遗漏索引目录 | 新版本找不到索引 | 将索引路径放入受保护运行数据目录并增加部署验证 |

## 13. 回滚方案

### 13.1 P1 回滚

- 保留旧 `customer_list_path` 和旧文件处理路径；
- active 白名单版本切回上一份 ready 版本；
- 禁用新索引读取开关；
- 不删除源白名单和旧索引。

### 13.2 P2 回滚

- 停止新 realtime ingestion worker；
- 保留 pending 文件和 processing lease；
- 临时恢复调度器直接处理模式；
- 不清理 inbox 和 `processed_files`。

### 13.3 P3–P5 回滚

- 进度字段和日志属于兼容性增强，可以保留；
- 批量导入失败时回退到已验证的索引构建实现；
- 查询结果异常时切回旧匹配路径，并记录回滚原因。

## 15. 最终验收场景

### 场景 A：大白名单持续输入

- 上传 412 万行白名单；
- 产生至少 100 个实时输入文件；
- 监听目录持续产生新文件；
- 要求监听不中断，文件最终全部进入终态。

### 场景 B：处理期间服务重启

- 在文件处理和 chunk 写入过程中执行 `systemctl restart`；
- 要求已完成 chunk 不重复生成任务；
- 未完成 chunk 自动恢复；
- 文件最终只能产生一套有效短信任务。

### 场景 C：白名单更新

- 文件 A 使用旧白名单版本开始处理；
- 上传并构建新白名单版本；
- 文件 B 使用新版本处理；
- 要求 A、B 的匹配依据可追溯且互不混淆。

### 场景 D：异常输入

- 输入文件格式错误；
- 白名单索引构建失败；
- 磁盘空间不足；
- 数据库短暂锁定；
- 要求错误分类正确、重试有退避、永久错误可人工处理。

### 场景 E：在线升级

- 在线更新期间存在 pending、processing 和 completed 文件；
- 要求数据库、白名单索引、inbox 和源监听目录不丢失；
- 服务恢复后继续处理；
- 更新 runner、systemd、应用日志和页面状态一致。
